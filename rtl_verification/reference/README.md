# 软件侧参考实现

不是测试向量的一部分，放在这里是为了让你们看到 **AME 在真实负载里怎么被使用**。
向量包里的 `prog.S` 是刻意展开、不含循环的最小激励，便于对波形；
这两个文件则是实际跑 LLM 时的样子。

## kernels_ame.c

一次完整 GEMM 的全部逻辑：

* **tile 三层循环** M/N/K 的分块顺序，以及 M、N、K 不满时的部分 tile 处理
* **K 维多次累加**：K=1024 时连做 32 条 `mfmacc` 累加进同一个累加器，
  中间不回写。真实负载里这是常态，而不是单条指令
* **操作数顺序** `mfmacc.s.bf16 acc0, tr1, tr0` 是 `(md, B, A)` ——
  第二个放右矩阵、第三个放左矩阵。写反得到的是转置结果
* **B 按 `[N,K]` 装载**，正好是 PyTorch 权重 `[out_features, in_features]`
  的布局，所以软件侧一次重排都不需要

## board.h

其中与你们相关的是缓存一致性部分：

**AME 的访存绕过 L1D 直接走 DDR**，而标量/向量访存经过 L1D，
硬件不维护两者一致性，只能软件显式同步。同步序列见 `kernels_ame.c`
里 `qwen3_gemm()` 的入口与出口，有两处容易搞反：

* GEMM **之后**不能对输出矩阵用 flush ——
  输出区可能残留 CPU 之前写的脏行，flush 会把它们写回 DDR，
  正好覆盖掉 AME 刚算出的结果。这件事必须在 GEMM **之前**做
* 全量 `l1d_inv_all` **直接丢弃脏行**，单独使用会连栈上未写回的数据
  一起丢掉，所以它前面必须先 `l1d_clean_all`

如果 RTL 侧对这两条的行为定义与上述不同，请告诉软件侧 —— 这直接影响正确性。
