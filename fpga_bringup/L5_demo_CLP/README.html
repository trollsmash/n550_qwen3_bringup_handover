L5 —— CLP（RVV 高速接口）版

与 L4_demo/ 只差一项：激活与 KV cache 改走 RVV 的 1024-bit 高速通路。其余全部相同（tile-major 权重、回答上限 256、 上下文 1024），就是为了做 A/B 对比。

文件与地址

文件写入地址
qwen3_s2c.bin0x80000000
w.bin0x88000000（tile-major，与 L4 同一份）
tok.bin0xD0000000（与 L4 同一份）

w.bin 和 tok.bin 与 L4 完全相同，只需换 qwen3_s2c.bin 即可在两版之间切换。

放开复位前，往 0x87F00014 写一个 uint32 = 当前 UTC 秒 （date +%s），提示符就会显示北京时间。板上没有 RTC，不授时则退回 显示开机时长，不影响运行。

⚠ 上板前必须先配好 NoC 重映射

程序假定：

RVV 访问 0x1000_0000 .. 0x1FFF_FFFF
   ↓ NoC 重映射（同一物理内存）
DDR      0xF000_0000 .. 0xFFFF_FFFF

RVV 走这个窗口绕过 L1 D-cache；AME 则直接用 0xF000_0000 段 （它本来就绕 L1D）。两条路径看到同一份数据，因此 GEMM 前后的 缓存维护指令被全部删除。

没配重映射就跑，启动时会被自检拦住并打印：

CLP 窗口 0x10000000 -> 0xF0000000  自检失败 rc=1
  rc=1: RVV 写入后 AME 视图读不到；rc=2: 反向读不到

自检是往 RVV 视图写魔数、从 AME 视图读回核对。没有这道检查的话， 映射配错的症状是"数值莫名不对"而不是崩溃，极难排查。

与 L4 的差异

L4L5 (CLP)
激活 / KV cache 位置0xD100_0000，RVV 经 L1D0x1000_0000 窗口，RVV 绕 L1D
GEMM 前后缓存维护每次 5 次全量 l1d_*_all无
g_abuf 的 BF16 转换标量循环RVV vfncvtbf16

第三项是被迫的：标量访存绕不开 L1 D-cache，若转换仍用标量， 数据会停在 cache 里，AME 从 DDR 视图读到旧值且不会有任何报错。

该看什么

每 token 省下的缓存维护约 25 ms（原来每 token 要做 980 次全量操作）。 更大的变量是高速接口的实际带宽 —— 它 1024-bit/事务、不发 burst、 outstanding 8，吞吐 = 128 B × 8 ÷ 延迟，全靠 outstanding 撑。

对比方法：同一个问题在 L4 和 L5 各跑一次，比 ms/token。 上下文越长差距应当越明显（KV 读取占比随之上升）。

已知的未尽事项

KV cache 的布局仍是 [layer][pos][kv_dim]，attention 读某个 KV head 时 每次只取 512 字节、且相邻位置跳 4096 字节 —— 只用掉 4/8 的 outstanding。 改成 [layer][kvh][pos][head_dim] 可让读取连续、填满 8 个，理论再快一倍。 这一项已列为 TODO，待本版实测带宽后再评估。
