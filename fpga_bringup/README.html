按这个顺序走，别跳级

每一级失败都直接指向一个子系统。跳过前面直接跑全模型，出了问题分不清是 PCIe、时钟、串口、矩阵单元还是模型本身——而全模型镜像 1.11 GB，加载一次就要等。

级别目录镜像大小验什么失败说明
L0L0_bringup/5.9 KBPCIe 写入、复位、取指、串口、RVV、AME、时钟板子基础通路
L1L1_ame_vectors/786 KBAME 矩阵单元数值正确性矩阵扩展实现
L2L2_L3_fullmodel/1.11 GB全模型前向，对黄金数据自检模型链路
L3同上 + tok.bin+3.3 MB中文进中文出的完整 demo—
L4L4_demo/1.11 GB同 L3，但权重是 tile-major 布局见下方说明

L4 与 L2/L3 的关系：功能完全相同，差别只有权重布局。两个目录各自成套， 固件与权重不能跨目录混用 —— 固件把权重总长编进了二进制并严格核对， 混用会在启动时报 QWEN3_ERR_SIZE。

L4 此刻不会更快：tile-major 把行间跨度从 K×2 变成 64 字节、整个 tile 连续 8 KB 且 4 KB 对齐，收益要等 RTL 支持「stride 等于数据位宽时合并 burst」 才能兑现。现在先上板，是为了确认这套布局在真机上数值正确， RTL 改完直接换目录就能见效，不必再等一轮软件。

源码在 src/，含全部 C/汇编与构建脚本，可以自己改地址、 加打印、重新编译。怎么编、最可能改哪几处、改地址时要避开什么坑， 见 src/BUILD.md。

L0 —— 先跑这个

看 L0_bringup/checklist.md（或 .html，可打印）。一页纸，含写入地址、 读回判读表、故障速查。

判成败只看一个地址：0x87F0001C（FAILMASK），为 0 才算过。 不要只看 STATUS——软失败后程序会继续跑，STATUS 会被后续阶段覆盖。

L0 第六步会回填性能采样数据（CYCLES / ITERS），把这两个数发回软件侧： 它们能把每 token 耗时从"0.2 秒到 3 秒"这个跨一个数量级的估算收敛成确定值。

L1 —— AME 数值

L1_ame_vectors/ 原本是给 RTL 验证同事的独立交付包，在板上同样能跑， 所以整份带上：L0 的 step5 只验了 1x1x32 全 1 这一种最简情形， 若全模型数值不对，需要更细的激励来定位是哪一类情况出错。

⚠ 该目录里的 README.md 是 RTL 视角（讲 testbench 与 $readmemh）。 上板请按下表操作，并且用 prog.bin 而不是 prog.hex —— 后者是给 Verilog $readmemh 的文本格式，后门写 DDR 用不了。 同一份说明也放了一份在 L1_ame_vectors/README_FPGA.md。

步骤操作
1PCIe 后门写 cases/<case>/prog.bin -> 0x8000_0000
2放开复位
3轮询 0x800C_0000，等它变成 0x600D600D（计算完成）
4读 0x800C_0004：0x50415353(PASS) / 0x4641494C(FAIL)
5失败时读 0x800C_0008 取首个不符元素的下标；0x800A_0000 起是结果矩阵 C

prog.bin 是从 0x8000_0000 起的完整连续镜像，代码、A、B、C、期望值全在里面， 一次装载就位 —— 不需要额外加载权重或分词器，也不用串口。流程与 L0 完全相同。

目录里的 a.bin / b.bin / c_ref.bin 不用另外装 —— 它们的内容已经在 prog.bin 里了， 单独留一份是为了排查时对照：后门读回输入区与 a.bin 比一下，就能分清 是后门没写进去还是 AME 算错了。详见 README_FPGA.md。

12 个 case（8 个纯 AME + 4 个 RVV/AME 混合）。先跑完前 8 个纯 AME 的， 再碰混合的 —— 后者涉及 cache 与 AME 之间的数据交换，前者不依赖 cache 行为。

L2 / L3 —— 全模型

地址见 addresses.txt。加不加 tok.bin 决定程序走哪条路：

加载了什么程序做什么用途
只有 w.bin回归模式：固定 4 个 token 跑一遍，与黄金数据自检L2。不依赖分词器，出问题范围更小
再加 tok.bin交互模式：串口输入中文，逐 token 吐回来L3，也是 demo 形态

L2 先不要加载 tok.bin，过了再加。

⚠ 本目录的固件每次只回答 1 个 token —— 那是源码默认值，为 QEMU 定的 （那里每多一个 token 就要再遍历一遍 1.1 GB 权重）。所以 L3 能验证的是 端到端形态跑得通：中文进得去、分词器认得出、答案吐得回来。

要看完整回答，用 L4_demo/，那一份编译时注入了 256 token（约 384 个汉字）。

交互模式怎么用

程序启动后停在 > 提示符，直接在串口终端里打字：

============ 交互模式 ============
直接输入中文问题后回车；输入数字选预置问题；q 退出
  1) 你好，请介绍一下你自己
  2) 用一句话解释什么是 RISC-V
  3) 写一首关于秋天的短诗

> 你好，请介绍一下你自己
[.....|.....|.....|.....|.....|...]您好，我是……

  [prompt 16 token，生成 28 token，14200 ms，507 ms/token]

>

方括号里的点是 28 层的推进过程，每 5 层一个分隔符 —— 卡住时能一眼看出停在第几层。 末尾那行速度是当场算出来的，不是估算。

几点提醒：

  • 串口终端要设成 UTF-8，否则中文回显是乱码。这与推理无关，纯粹是终端配置。
  • 权重要提前灌好。1.11 GB 走后门写进 DDR 不是几秒的事， 演示前让程序跑起来停在提示符，现场只做输入输出。
  • 现场用输入法打中文有卡壳风险，预置问题按数字键直接触发，手输作为加分项。
  • 每轮生成多少 token 由编译期的 CHAT_MAX_GEN 决定（默认 1）。 按实测速度调：一个 token 若要 10 秒，就压到 5~8 个说一句短话。
  • 每轮都从头 prefill，不保留上下文 —— 每轮独立反倒让现场更可控。

三条通用注意事项

一、反复换镜像时先断电。 本核有 32 KB L1I，与 D-cache 不自动一致；host 经 PCIe 写镜像对 CPU 而言 就是"动态加载指令"。软复位时 I-cache 里可能还留着上一个镜像的指令， 现象是"明明重新烧了，行为一点没变"。start.S 里有 fence.i 兜底， 但遇到无法解释的"改了没生效"，先断电重来再怀疑代码。

二、传输后先校验。 1.11 GB 的权重经 U 盘或网络传过去，损坏不会有任何提示， 上板后表现为"权重 magic 不对"，或者更糟——算出一堆垃圾还不报错。

md5sum -c checksums.md5 # Linux / WSL，全绿才继续 # Windows: certutil -hashfile L2_L3_fullmodel\w.bin MD5

MANIFEST.txt 是同一份信息的人读版本，带文件大小， 扫一眼就能看出哪个文件没传全。

三、串口没输出不代表失败。 观测主通道是 mailbox（PCIe 可回读 DDR），串口只是辅助。 先读 mailbox 再怀疑程序。

出问题时带上这些信息

  • mailbox 全部字段的读回值（见 L0_bringup/checklist.md 的字段表）
  • 串口完整日志（若有）
  • 若串口打出 *** TRAP ***：现场会完整打印六个寄存器加两项诊断。

先看 mtval 与 [mepc] 这两行，它们来自不同通路：

行来自哪条通路
mtvalCPU 取指拿到的指令编码
[mepc]同一地址用 load 读回的内容（走 D-cache / DDR）

两者一致 → 指令本身有问题，拿 mepc 去同目录 .diss 搜地址， 能看到出错指令与对应的 C 源码行；.sym 是按地址排序的符号表，可先定位到函数。 两者不一致 → 取指与数据读看到的不是同一份内容，问题在 I-cache 而非代码。

随后 handler 会执行一次 fence.i 并返回原处重试（最多 3 次）。 刷新后能继续跑就坐实了 I-cache 与 DDR 不同步；照样 trap 则说明不在 I-cache。

ra 是调用者地址，sp 看栈有没有跑飞， mstatus 的 FS/VS/MS 三个域应各为 01（扩展已使能）。

同一份现场也写进 mailbox 0x87F00040 起的六个字 （mcause / mepc / mtval / mstatus / ra / sp），顺序在打串口之前 —— 串口若在打印途中挂掉，host 后门仍能把现场完整取走。

  • 想确认「真出事时能不能看到现场」，用 -DTRAP_TEST 编一版 L0： 它在 step2 之后故意执行一条非法指令，把整套流程走一遍。默认不编入。
