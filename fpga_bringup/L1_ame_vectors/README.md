# AME 矩阵扩展 — RTL 验证向量包 v1

面向 **RTL 验证**。你不需要了解上层的 LLM 项目，也不需要装它的软件环境。

每个 case 是一段**能自己跑起来的最小裸机程序**：算完把结果写到固定地址，
再往一个标志地址写魔数。你的 testbench 只要"装镜像 → 放复位 → 等标志 → dump 内存"。

---

## 一、5 分钟跑通

```
cases/001_bf16_full_tile/prog.hex     ← 装进内存，起始地址 0x8000_0000
```

`prog.hex` 是**从基址开始的完整连续内存镜像**，每行一个 32 位小端字，
`$readmemh` 直接可读。代码、A、B、C、期望值全在里面，一次装载就位。

```verilog
$readmemh("prog.hex", mem);        // mem[0] 对应物理地址 0x8000_0000
```

放开复位，然后轮询：

| 地址 | 含义 |
|---|---|
| `0x800C_0000` | 计算完成标志。等它变成 `0x600D600D` |
| `0x800C_0004` | 程序自检结果：`0x50415353`(`PASS`) / `0x4641494C`(`FAIL`) |
| `0x800C_0008` | 首个不符元素的下标；全对时为 `-1` |
| `0x800A_0000` | 结果矩阵 C 的起始地址 |

**自检是附赠的，不是必须用的。** 镜像里带了一份期望值，程序算完会自己比一遍。
你也可以完全无视它，只等 `0x800C_0000` 的魔数，然后 dump C 区自己比对：

```
python3 check.py 001 你dump出来的.hex
```

所有 case 的地址表**完全一致**，testbench 写一次就够，换 case 只换 `prog.hex`。
混合 case（009+）多用了几个字段，见下面第二·五节，地址同样固定。

## 二、Case 清单

分两组，**先把第一组全部跑绿，再碰第二组**。

### 第一组：纯 AME（001–008）

只有 AME 与标量指令，**完全不依赖 cache 行为**——数据由 testbench 直接装进内存。
这是它们的价值所在：**cache 子系统还没做好时，矩阵单元本身的正确性照样能验**。

| # | 名称 | M | N | K | mfmacc | 为什么有这一条 |
|---|---|---|---|---|---|---|
| 001 | bf16_full_tile | 128 | 128 | 32 | 1 | 满 tile 基线，覆盖 16384 个输出的完整通路 |
| 002 | m1_gemv | 1 | 128 | 1024 | 32 | LLM 逐 token 生成时的真实形状，tile 只填 1/128 |
| 003 | partial_m | 7 | 128 | 32 | 1 | M 非 2 的幂。用 7 是为了让隐式的 2 的幂假设立刻失效 |
| 004 | k_multiblock | 128 | 128 | 256 | 8 | 多条 mfmacc 累加进同一累加器，验块间舍入 |
| 005 | partial_n | 128 | 13 | 32 | 1 | N 方向的部分 tile 与 M 方向走不同路径，须分开验 |
| 006 | partial_k | 128 | 128 | 17 | 1 | K 不满一块。剩余乘法单元必须贡献 0 而非残留值 |
| 007 | stride_gap | 128 | 128 | 32 | 1 | A/B 行 stride 大于列数。忽略 stride 的实现只在这里错 |
| 008 | massive_act | 128 | 128 | 1024 | 32 | 真实数值分布 + ±6912 outlier，压测动态范围与 32 次累加 |

**001 不过就别看后面的**——它失败说明是根本性问题。
008 的 K=1024 意味着 32 轮 tile 装载，仿真最慢，建议放这一组最后。

### 第二组：RVV 与 AME 混合（009–011）

引入 RVV、缓存同步与访存定序。真实负载就长这样：模型每层要在
RVV 与 AME 之间来回交接七次。

| # | 名称 | 验什么 | 判据 |
|---|---|---|---|
| 009a | rvv_ame_handoff_cbo | 双向交接，缓存用 **Zicbom**（`cbo.clean`/`cbo.inval`） | `status` + `stage_a`/`stage_b` |
| 009b | rvv_ame_handoff_l1d | 同上，缓存换成 **xdcache** 全量（`l1d_clean_all`/`l1d_inv_all`） | 同上 |
| 010 | sync_sensitivity | 同一计算带同步/不带同步各做一遍 | **只看 `status`**，两个 probe 是观察项 |
| 011 | fence_ordering | AME 写完立刻读，带 `fence`/不带各一次 | **只看 `status`**，同上 |

**009 为什么有两个变体**：软件侧 QEMU 走 `cbo.*`、真机走 `l1d_*_all`。
如果 RTL 只实现了其中一套，我们要到上板那天才会发现。两个都要过。

> `009b` 在 QEMU 上跑不了——`l1d_clean_all` 在那里是非法指令（实测 `mtval=0x0010702b`）。
> 这是预期行为，不是缺陷。

## 二·五、混合 case 的判读

除通用的 `done` / `status` 外，多出这几个字（地址见各 case 的 `meta.json` 的 `segments`）：

| 字段 | 含义 |
|---|---|
| `stage_a` | 阶段 A（RVV 写 → clean → AME 读）完成标志 |
| `stage_b` | 阶段 B（AME 写 → inval → RVV 读）完成标志 |
| `xor` / `xor_ref` | RVV 对 C 做的 XOR 校验和及其期望值 |
| `probe1` / `probe2` | 010/011 的两次结果 |
| `probe_eq` | 两次是否相同：1=相同 0=不同 |
| `trap_cause` / `trap_epc` / `trap_tval` | 异常信息，正常时全 0 |

**拆成 `stage_a`/`stage_b` 两段是有意的**：整条链只报一个 PASS/FAIL 的话，
失败时分不清是 clean 没把数据写回 DDR，还是 inval 没把旧拷贝清掉——
这在 RTL 里是两处不同的实现。

* `stage_a` 未置位 ⇒ 卡在 RVV→AME 方向，多半是 **clean 没生效**，AME 读到了旧值
* `stage_b` 未置位或 `xor` 不符 ⇒ 卡在 AME→RVV 方向，多半是 **inval 没生效**，RVV 命中了 L1D 里的旧拷贝

校验和用 XOR 而不是浮点求和，是因为 RVV 的归约顺序是实现定义的：
浮点求和会因归约树不同给出不同低位，期望值根本没法定。XOR 可交换可结合，
任意归约顺序都得到同一个值，判据才能是 bit-exact。

### ⚠ 关于 010 和 011 的观察项

`probe2`（不带同步 / 不带 fence 那次）**永远不作判据**。它的结果依赖 cache
当时的状态、流水线时序、写缓冲深度，当判据只会得到随机的红绿灯。

* **两次不同** ⇒ 证明软件同步确实必要，且软件用的序列确实有效
* **两次相同** ⇒ **不能推出"不需要同步"**。可能只是数据恰好没驻留 cache，
  或恰好没撞上时序窗口

**请不要拿"不加同步也过了"去论证软件可以省掉同步**——那是最危险的误读。
（在 QEMU 上 011 的两次就是相同的，因为它根本不模拟写缓冲时序。）

## 三、数据布局（最容易搞错的地方）

```
C[M][N] = A[M][K] · B[N][K]ᵀ          全部行主序
```

**B 是 `[N,K]` 不是 `[K,N]`。** 装载时 A 按 `mtilem × mtilek`，B 按 `mtilen × mtilek`。
这不是笔误：`[N,K]` 正好是 PyTorch 权重 `[out_features, in_features]` 的布局，
所以软件侧一次重排都不需要。

`a.hex` / `b.hex` / `c_ref.hex` 是各矩阵单独的内存镜像，格式同样是每行 32 位小端字：

* `a.hex`、`b.hex` —— 一行装两个 BF16，**低 16 位是下标偶数的那个**
* `c_ref.hex` —— 一行一个 FP32 位模式

行 stride 见 `meta.json` 的 `stride_bytes`。**注意 007 的 stride 大于实际列数**，
行与行之间有空隙，必须严格按 stride 寻址。

指令序列直接看 `prog.S`，它是完全展开的——没有循环，没有分支，
除了 tile 装载、`mfmacc` 和几条 `li` 之外什么都没有，波形能逐条对上。

## 四、期望值是怎么来的

**不是从另一个模拟器抄的。** 参考值由架构语义推导（`tools/40_gen_ame_vectors.py`），
理由是：拿一个实现去验另一个实现，两边的错误会互相掩盖。
我们用的 QEMU 模型就被证实存在缺陷（`mzero` 曾只清累加器前 64 行）。

参考模型只有三条规则，实测确定：

1. **单条 `mfmacc` 内部，K 维累加精度宽于 FP32。**
   构造 `A=[2²⁴, 1×31]`、`B=全1` 时，31 个 `1.0` 一个都没被吞掉——
   若是 FP32 逐项累加它们会全部消失。所以块内按精确有理数求和，最后才舍入。

2. **跨多条 `mfmacc` 时，累加器中间值落回 FP32。**
   第二条 `mfmacc` 贡献的 `1.0`（远小于该量级 1 ULP=2）被整个吞掉。
   所以按 K=32 分块，**块间按 FP32 舍入后再累加**。

3. **舍入按 IEEE RNE**（最近偶数）。

写成代码就是：

```python
for 每个 K 块（32 个元素）:
    块和 = Σ A[m,k] × B[n,k]        # 精确，零误差
    acc  = fp32_rne(acc + 块和)      # 每块结束舍入一次
```

这三条已用 QEMU 交叉验证：纯 AME 的 8 个 case 共 **84608 个输出元素，逐位相同，零 ULP 偏差**。
混合 case 另在 QEMU 上实跑验证过（009a/010/011 全部 PASS，XOR 校验和与参考值一致）。
所以规范本身是可信的；如果你的 RTL 对不上，先怀疑 RTL。

## 五、判据

主判据是**归一化误差**，不是 ULP 数：

```
归一化误差 = |实测 - 期望| / c_peak      <=  meta.json 的 norm_tol
```

`c_peak.hex` 给出每个输出点在累加过程中**部分和达到过的最大绝对值**。

### 为什么不直接用 ULP

舍入误差是在累加过程的量级上产生的，而 ULP 是相对**最终值**算的。
当一个输出点的正负项大量抵消（最终值远小于中间量级）时，同一个绝对误差
换算成 ULP 会被放大几个数量级——**一个完全正常的实现也会报出上万 ULP**。

008 里就有这样一个点：

```
(126,63)   部分和峰值 44865   最终值 1.427   抵消比 31435 倍
           绝对误差 0.00283 = 中间量级的 0.7 个 ULP     ← 正常
                            = 最终值的 23774 个 ULP     ← 吓人但无意义
```

各 case 的抵消情况（`meta.json` 的 `cancellation`）：

| case | 中位抵消比 | 最大抵消比 | 高抵消点 |
|---|---|---|---|
| 001–007 | 1.00x | ~1.0x | 0 |
| **008 massive_act** | 1.48x | **31435x** | **16** |

只有 008 需要关心这件事——它的数据刻意复现了 Qwen3 深层的 massive activation
（99% 的元素在 1~3 之间，1% 是 ±6912），这种分布必然产生抵消。

### 阈值怎么来的

```
norm_tol = 2 × K块数 × 2^-24
```

K 每 32 个元素一块，每个块边界最多引入半个 ULP（`2^-24`）的舍入，
再留 2 倍余量容纳实现之间合理的舍入点差异。**不是拍脑袋的常数**，
`meta.json` 的 `norm_tol_note` 里写了推导。

### check.py 的三种结论

* **PASS 完全一致** —— 逐位相同
* **PASS（按归一化误差判据）** —— 有点 ULP 超标，但归一化误差在阈值内。
  会列出抵消最严重的几个点供核对。这**不是**降低标准：它说明实现的累加
  精度合格，差异来自舍入点位置，不是算错了
* **FAIL** —— 归一化误差也超标，是真实的精度或逻辑问题

> 若你的 RTL 落在第二类，说明累加器的位宽/舍入点与参考模型不同但精度合格。
> 要做到逐位一致，需与架构组确认累加器的确切语义，而不是去改那几个点。
> 顺带一提，参考模型的"块间落回 FP32"这一条是在 QEMU 上探测出来的，
> QEMU 是模拟器，未必等于硬件——真有分歧时以架构定义为准。

## 六、三条硬约束（都是踩出来的）

1. **`mstatus.MS`（bit 30:29）必须使能**，否则所有 AME 指令报 illegal instruction。
   现象与"指令编码不支持"一模一样，极容易误判成译码问题。
   `prog.S` 开头已经设好了 `FS | VS | MS`。

2. **tile 装载会读满整个 tile 的地址范围**，即使 `mtilem=1` 也一样。
   给 A/B 分配缓冲时尾部必须留出余量（我们用 8 KB），
   按有效数据大小紧贴分配会读到非法地址。
   如果你的 testbench 在 A/B 之后立刻放了别的东西，注意这一条。

3. **`frm` 要显式写。** 参考值按 RNE 生成，`prog.S` 里有 `csrw frm, x0`。
   不写就得看复位默认值，各家实现不一定相同。

## 七、对不上的时候

```
python3 check.py <case> <你dump出来的文件>
```

只依赖 Python 标准库，不需要 numpy。它不只报 PASS/FAIL，还会把失败模式翻译成原因：

* 输出区全是 `0xA5A5A5A5` → `msce32` 没执行，或写到了别的地址
  （C 区在镜像里预置了这个值，就是为了让"漏写"和"写了个 0"能区分开）
* 只有第 0 行对 → `mtilem` 没生效，矩阵单元只算了一行
* 正好前一半行对 → 累加器清零只覆盖了一半
* 结果与期望值的**转置**吻合 → `mfmacc` 操作数顺序写反了。
  正确写法是 `mfmacc.s.bf16 md, B, A`：第二个操作数放右矩阵，第三个放左矩阵
* 零散位置漏写 → 查回写 stride

## 九、需要改基址 / 加 case 的话

生成器就在包里（`golden_src/`），本包是自包含的，不需要上层项目。

基址不是 `0x8000_0000` 的话：

```
python3 golden_src/40_gen_ame_vectors.py --base 0x<你的基址> --out .
source <你的工具链环境>            # 需要 $RISCV_ISA / $CROSS
golden_src/41_build_vectors.sh
```

本包用的构建参数记在 **`BUILD_INFO.txt`** 里（march、mabi、编译器版本，
以及每段扩展缺失时的症状）。`prog.elf` 的 `.riscv.attributes` 段被链接脚本
丢弃了（为了让 objcopy 出的镜像干净），所以无法从二进制反查，请看那个文件。

march 是：

```
rv64gcv_zfh_zfbfmin_zvfh_zvfbfmin_zvfbfwma_xewmatrix1p0_zicbom_zicbop_zicboz_xdcache
```

只改基址的话其实**不必重新汇编**：`a.hex` / `b.hex` / `c_ref.hex` 与地址无关，
只有 `prog.hex` 里的绝对地址需要重生成。

段布局在 `40_gen_ame_vectors.py` 的 `SEG` 表里，`meta.json` 会同步反映。
新增 case 只需在同一文件的 `CASES` 列表里加一行——参考值会自动按上面
第四节的规范算出来，不需要手工填期望值。

数据用固定种子的 xorshift 生成，**任何机器上重跑都得到逐位相同的结果**。

## 十、还没覆盖的

诚实说明，避免误以为这包验完就万事大吉：

* **RVV 与 AME 的并发执行未覆盖**：009-011 验的是顺序交接（一方做完另一方再开始），
  没有验 AME 计算期间 CPU 同时跑 RVV 的情形。若硬件允许两者重叠，那是另一类激励。
* **INT8×INT8→INT32 未覆盖**（本包只有 BF16）。硬件支持 INT8 且 K=64，
  但上层项目走的是 BF16 路线，没有可信的参考实现，硬造风险更大。需要的话可以补。
* **Inf / NaN / 非规格化数未覆盖。** 需要先和架构组确认这些输入下的期望行为，
  规范不明确时造出来的向量只会制造争议。
* **时序、背靠背发射、accumulator 冲突未覆盖。** 本包验的是数值正确性，
  流水线相关的验证需要另一类激励。
* **`mrelease` 的语义未单独验证**，只在每个 case 末尾出现一次。

有问题直接找软件侧，把 `check.py` 的完整输出带上。
