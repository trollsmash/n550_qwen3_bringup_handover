# AME 矩阵扩展 — RTL 验证向量包 v1

面向 **RTL 验证**。你不需要了解上层的 LLM 项目，也不需要装它的软件环境。

每个 case 是一段**能自己跑起来的最小裸机程序**：算完把结果写到固定地址，
再往一个标志地址写魔数。你的 testbench 只要"装镜像 → 放复位 → 等标志 → dump 内存"。

---

## 一、5 分钟跑通

```
cases/001_bf16_full_tile/prog.hex     ← 装进内存，起始地址 0x8000_0000
```

`prog.hex` 是**从基址开始的完整连续内存镜像**，每行一个 32 位小端字，
`$readmemh` 直接可读。代码、A、B、C、期望值全在里面，一次装载就位。

```verilog
$readmemh("prog.hex", mem);        // mem[0] 对应物理地址 0x8000_0000
```

放开复位，然后轮询：

| 地址 | 含义 |
|---|---|
| `0x800C_0000` | 计算完成标志。等它变成 `0x600D600D` |
| `0x800C_0004` | 程序自检结果：`0x50415353`(`PASS`) / `0x4641494C`(`FAIL`) |
| `0x800C_0008` | 首个不符元素的下标；全对时为 `-1` |
| `0x800A_0000` | 结果矩阵 C 的起始地址 |

**自检是附赠的，不是必须用的。** 镜像里带了一份期望值，程序算完会自己比一遍。
你也可以完全无视它，只等 `0x800C_0000` 的魔数，然后 dump C 区自己比对：

```
python3 check.py 001 你dump出来的.hex
```

八个 case 的地址表**完全一致**，testbench 写一次就够，换 case 只换 `prog.hex`。

## 二、Case 清单

按顺序跑。**001 不过就别看后面的**——它失败说明是根本性问题。

| # | 名称 | M | N | K | mfmacc 条数 | 为什么有这一条 |
|---|---|---|---|---|---|---|
| 001 | bf16_full_tile | 128 | 128 | 32 | 1 | 满 tile 基线，覆盖 16384 个输出的完整通路 |
| 002 | m1_gemv | 1 | 128 | 1024 | 32 | LLM 逐 token 生成时的真实形状，tile 只填 1/128 |
| 003 | partial_m | 7 | 128 | 32 | 1 | M 非 2 的幂。用 7 是为了让隐式的 2 的幂假设立刻失效 |
| 004 | k_multiblock | 128 | 128 | 256 | 8 | 多条 mfmacc 累加进同一累加器，验块间舍入 |
| 005 | partial_n | 128 | 13 | 32 | 1 | N 方向的部分 tile 与 M 方向走不同路径，须分开验 |
| 006 | partial_k | 128 | 128 | 17 | 1 | K 不满一块。剩余乘法单元必须贡献 0 而非残留值 |
| 007 | stride_gap | 128 | 128 | 32 | 1 | A/B 行 stride 大于列数。忽略 stride 的实现只在这里错 |
| 008 | massive_act | 128 | 128 | 1024 | 32 | 真实数值分布 + ±6912 outlier，压测动态范围与 32 次累加 |

规模提示：001/004/006/007 的镜像 786 KB；002/003/005 略小；
008 的 K=1024 意味着 32 轮 tile 装载，仿真时间最长，建议放最后。

## 三、数据布局（最容易搞错的地方）

```
C[M][N] = A[M][K] · B[N][K]ᵀ          全部行主序
```

**B 是 `[N,K]` 不是 `[K,N]`。** 装载时 A 按 `mtilem × mtilek`，B 按 `mtilen × mtilek`。
这不是笔误：`[N,K]` 正好是 PyTorch 权重 `[out_features, in_features]` 的布局，
所以软件侧一次重排都不需要。

`a.hex` / `b.hex` / `c_ref.hex` 是各矩阵单独的内存镜像，格式同样是每行 32 位小端字：

* `a.hex`、`b.hex` —— 一行装两个 BF16，**低 16 位是下标偶数的那个**
* `c_ref.hex` —— 一行一个 FP32 位模式

行 stride 见 `meta.json` 的 `stride_bytes`。**注意 007 的 stride 大于实际列数**，
行与行之间有空隙，必须严格按 stride 寻址。

指令序列直接看 `prog.S`，它是完全展开的——没有循环，没有分支，
除了 tile 装载、`mfmacc` 和几条 `li` 之外什么都没有，波形能逐条对上。

## 四、期望值是怎么来的

**不是从另一个模拟器抄的。** 参考值由架构语义推导（`tools/40_gen_ame_vectors.py`），
理由是：拿一个实现去验另一个实现，两边的错误会互相掩盖。
我们用的 QEMU 模型就被证实存在缺陷（`mzero` 曾只清累加器前 64 行）。

参考模型只有三条规则，实测确定：

1. **单条 `mfmacc` 内部，K 维累加精度宽于 FP32。**
   构造 `A=[2²⁴, 1×31]`、`B=全1` 时，31 个 `1.0` 一个都没被吞掉——
   若是 FP32 逐项累加它们会全部消失。所以块内按精确有理数求和，最后才舍入。

2. **跨多条 `mfmacc` 时，累加器中间值落回 FP32。**
   第二条 `mfmacc` 贡献的 `1.0`（远小于该量级 1 ULP=2）被整个吞掉。
   所以按 K=32 分块，**块间按 FP32 舍入后再累加**。

3. **舍入按 IEEE RNE**（最近偶数）。

写成代码就是：

```python
for 每个 K 块（32 个元素）:
    块和 = Σ A[m,k] × B[n,k]        # 精确，零误差
    acc  = fp32_rne(acc + 块和)      # 每块结束舍入一次
```

这三条已用 QEMU 交叉验证：8 个 case 共 **84608 个输出元素，逐位相同，零 ULP 偏差**。
所以规范本身是可信的；如果你的 RTL 对不上，先怀疑 RTL。

## 五、判据

**bit-exact。** 逐位相同才算过。

唯一的例外：真值恰好落在两个相邻 FP32 正中间时，允许差 1 ULP。
`check.py` 会把这种情况单独统计并标注，不计入失败。

> 已知问题：我们用的 QEMU 模型在这种中点情形下**舍入方向不稳定**——
> 同一份数据两次执行会给出 `16777246` 和 `16777248` 两个不同结果。
> 这是 QEMU 的缺陷，不代表架构语义。如果你的 RTL 在中点上与参考值差 1 ULP，
> 这是需要和架构组确认的点，不是 RTL bug。

## 六、三条硬约束（都是踩出来的）

1. **`mstatus.MS`（bit 30:29）必须使能**，否则所有 AME 指令报 illegal instruction。
   现象与"指令编码不支持"一模一样，极容易误判成译码问题。
   `prog.S` 开头已经设好了 `FS | VS | MS`。

2. **tile 装载会读满整个 tile 的地址范围**，即使 `mtilem=1` 也一样。
   给 A/B 分配缓冲时尾部必须留出余量（我们用 8 KB），
   按有效数据大小紧贴分配会读到非法地址。
   如果你的 testbench 在 A/B 之后立刻放了别的东西，注意这一条。

3. **`frm` 要显式写。** 参考值按 RNE 生成，`prog.S` 里有 `csrw frm, x0`。
   不写就得看复位默认值，各家实现不一定相同。

## 七、对不上的时候

```
python3 check.py <case> <你dump出来的文件>
```

只依赖 Python 标准库，不需要 numpy。它不只报 PASS/FAIL，还会把失败模式翻译成原因：

* 输出区全是 `0xA5A5A5A5` → `msce32` 没执行，或写到了别的地址
  （C 区在镜像里预置了这个值，就是为了让"漏写"和"写了个 0"能区分开）
* 只有第 0 行对 → `mtilem` 没生效，矩阵单元只算了一行
* 正好前一半行对 → 累加器清零只覆盖了一半
* 结果与期望值的**转置**吻合 → `mfmacc` 操作数顺序写反了。
  正确写法是 `mfmacc.s.bf16 md, B, A`：第二个操作数放右矩阵，第三个放左矩阵
* 零散位置漏写 → 查回写 stride

## 九、需要改基址 / 加 case 的话

生成器就在包里（`golden_src/`），本包是自包含的，不需要上层项目。

基址不是 `0x8000_0000` 的话：

```
python3 golden_src/40_gen_ame_vectors.py --base 0x<你的基址> --out .
source <你的工具链环境>            # 需要 $RISCV_ISA / $CROSS
golden_src/41_build_vectors.sh
```

只改基址的话其实**不必重新汇编**：`a.hex` / `b.hex` / `c_ref.hex` 与地址无关，
只有 `prog.hex` 里的绝对地址需要重生成。

段布局在 `40_gen_ame_vectors.py` 的 `SEG` 表里，`meta.json` 会同步反映。
新增 case 只需在同一文件的 `CASES` 列表里加一行——参考值会自动按上面
第四节的规范算出来，不需要手工填期望值。

数据用固定种子的 xorshift 生成，**任何机器上重跑都得到逐位相同的结果**。

## 十、还没覆盖的

诚实说明，避免误以为这包验完就万事大吉：

* **INT8×INT8→INT32 未覆盖**（本包只有 BF16）。硬件支持 INT8 且 K=64，
  但上层项目走的是 BF16 路线，没有可信的参考实现，硬造风险更大。需要的话可以补。
* **Inf / NaN / 非规格化数未覆盖。** 需要先和架构组确认这些输入下的期望行为，
  规范不明确时造出来的向量只会制造争议。
* **时序、背靠背发射、accumulator 冲突未覆盖。** 本包验的是数值正确性，
  流水线相关的验证需要另一类激励。
* **`mrelease` 的语义未单独验证**，只在每个 case 末尾出现一次。

有问题直接找软件侧，把 `check.py` 的完整输出带上。
