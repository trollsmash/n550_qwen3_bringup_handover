## 按这个顺序走，别跳级

每一级失败都直接指向一个子系统。**跳过前面直接跑全模型，出了问题分不清是
PCIe、时钟、串口、矩阵单元还是模型本身**——而全模型镜像 1.11 GB，加载一次就要等。

| 级别 | 目录 | 镜像大小 | 验什么 | 失败说明 |
|---|---|---|---|---|
| **L0** | `L0_bringup/` | 4.8 KB | PCIe 写入、复位、取指、串口、RVV、AME、时钟 | 板子基础通路 |
| **L1** | `L1_ame_vectors/` | 786 KB | AME 矩阵单元数值正确性 | 矩阵扩展实现 |
| **L2** | `L2_L3_fullmodel/` | 1.11 GB | 全模型前向，对黄金数据自检 | 模型链路 |
| **L3** | 同上 + `tok.bin` | +3.3 MB | 中文进中文出的完整 demo | — |

### L0 —— 先跑这个

看 `L0_bringup/checklist.md`（或 `.html`，可打印）。一页纸，含写入地址、
读回判读表、故障速查。

**判成败只看一个地址**：`0x87F0001C`（FAILMASK），为 0 才算过。
不要只看 STATUS——软失败后程序会继续跑，STATUS 会被后续阶段覆盖。

L0 第六步会回填性能采样数据（`CYCLES` / `ITERS`），**把这两个数发回软件侧**：
它们能把每 token 耗时从"0.2 秒到 3 秒"这个跨一个数量级的估算收敛成确定值。

### L1 —— AME 数值

`L1_ame_vectors/` 原本是给 RTL 验证同事的独立交付包，**在板上同样能跑**，
所以整份带上：L0 的 step5 只验了 1x1x32 全 1 这一种最简情形，
若全模型数值不对，需要更细的激励来定位是哪一类情况出错。

⚠ 该目录里的 `README.md` 是 **RTL 视角**（讲 testbench 与 `$readmemh`）。
上板请按下表操作，并且**用 `prog.bin` 而不是 `prog.hex`** ——
后者是给 Verilog `$readmemh` 的文本格式，后门写 DDR 用不了。
同一份说明也放了一份在 `L1_ame_vectors/README_FPGA.md`。

| 步骤 | 操作 |
|---|---|
| 1 | PCIe 后门写 `cases/<case>/prog.bin` -> `0x8000_0000` |
| 2 | 放开复位 |
| 3 | 轮询 `0x800C_0000`，等它变成 `0x600D600D`（计算完成） |
| 4 | 读 `0x800C_0004`：`0x50415353`(PASS) / `0x4641494C`(FAIL) |
| 5 | 失败时读 `0x800C_0008` 取首个不符元素的下标；`0x800A_0000` 起是结果矩阵 C |

`prog.bin` 是从 `0x8000_0000` 起的完整连续镜像，代码、A、B、C、期望值全在里面，
一次装载就位 —— 不需要额外加载权重或分词器，也不用串口。流程与 L0 完全相同。

目录里的 `a.bin` / `b.bin` / `c_ref.bin` **不用另外装** —— 它们的内容已经在 `prog.bin` 里了，
单独留一份是为了排查时对照：后门读回输入区与 `a.bin` 比一下，就能分清
是后门没写进去还是 AME 算错了。详见 `README_FPGA.md`。

12 个 case（8 个纯 AME + 4 个 RVV/AME 混合）。**先跑完前 8 个纯 AME 的**，
再碰混合的 —— 后者涉及 cache 与 AME 之间的数据交换，前者不依赖 cache 行为。

### L2 / L3 —— 全模型

地址见 `addresses.txt`。**L2 先不要加载 `tok.bin`**：
不加载时程序走回归模式，用固定的 4 个 token 跑一遍并与黄金数据自检，
不依赖分词器，出问题的范围更小。L2 过了再加 `tok.bin` 跑 L3。

## 三条通用注意事项

**一、反复换镜像时先断电。**
本核有 32 KB L1I，与 D-cache 不自动一致；host 经 PCIe 写镜像对 CPU 而言
就是"动态加载指令"。软复位时 I-cache 里可能还留着上一个镜像的指令，
现象是"明明重新烧了，行为一点没变"。`start.S` 里有 `fence.i` 兜底，
但遇到无法解释的"改了没生效"，**先断电重来再怀疑代码**。

**二、传输后先校验。**
1.11 GB 的权重经 U 盘或网络传过去，损坏不会有任何提示，
上板后表现为"权重 magic 不对"，或者更糟——算出一堆垃圾还不报错。

    md5sum -c checksums.md5          # Linux / WSL，全绿才继续
    # Windows: certutil -hashfile L2_L3_fullmodel\w.bin MD5

`MANIFEST.txt` 是同一份信息的人读版本，带文件大小，
扫一眼就能看出哪个文件没传全。

**三、串口没输出不代表失败。**
观测主通道是 mailbox（PCIe 可回读 DDR），串口只是辅助。
先读 mailbox 再怀疑程序。

* mailbox 全部字段的读回值（见 `L0_bringup/checklist.md` 的字段表）
* 串口完整日志（若有）
* 若串口打出 `*** TRAP ***`：拿 `mepc` 直接在同目录的 `.diss`（源码交织反汇编）里搜该地址，就能看到出错指令与对应的 C 源码行；`.sym` 是按地址排序的符号表，可先确定落在哪个函数。记下 `mcause` / `mepc` / `mtval` 三个值，
  软件侧可用配套的 `.elf` 定位到源码行
* 用的是哪一级、镜像的 md5
