# L6_noame —— 用 RVV 替换 AME 的对照组

**这不是更快的版本，是一把尺子。** 它把 [`L6_demo_opt/`](../L6_demo_opt/)
里所有走 AME 的矩阵乘换成 RVV 实现，其余一概不动，用来量出 AME 在真实
负载里到底贡献了多少。

## 唯一的变量

| | L6_demo_opt | L6_noame |
|---|---|---|
| 矩阵乘计算单元 | **AME**（`kernels_ame.c`） | **RVV**（`kernels_rvvtile.c`） |
| 权重 | tile-major | tile-major，**同一份文件** |
| 非矩阵算子 | `ops_rvv.c` | 同左，未改 |
| CLP 窗口 | 启用 | 同左 |
| 访存优化 | attention 批处理 + rope 连续访存 | 同左 |
| 回答上限 / 上下文 | 256 / 1024 | 同左 |

两版**输出逐位相同** —— QEMU 回归取到同一组 token
（`3837 101889 106525 56568 32664`）。所以时间差纯粹来自计算单元。

## 文件与地址

| 文件 | 写入地址 |
|---|---|
| `qwen3_s2c.bin` | 0x80000000 |
| `w.bin` | 0x88000000 |
| `tok.bin` | 0xD0000000 |

`w.bin` 与 L4/L5/L6 是**同一份 tile-major 权重**（md5 相同），本目录自带一份
以便独立使用。CLP 窗口的重映射要求与 L5/L6 一致。

## 为什么 RVV 版仍然读 tile-major 权重

按行优先重排一份权重给 RVV 会跑得更快，但那样测出来的差距里就混进了
**两个**变量：计算单元不同、权重布局不同。而布局本身值好几倍
（tile-major 能命中 MLSU 的行合并，row-major 命中不了），两者搅在一起，
结论说不清楚。

所以这一版读同一份权重，代价是布局对向量单元并不合身：

* 一块 tile 是 128 行 × 32 列，照着 AME 的 TR 寄存器定的。
  AME 一条 `mfmacc` 把整块吞下去；RVV 没有这种指令，只能拆成
  **128 个长度 32 的点积**，每个都要单独归约。
* K=32 时 `e16m1` 的 vlmax 是 64，**只填了一半**。

这个劣势是布局与指令形态不匹配的必然结果，不是实现没写好 ——
恰恰是对比想要量出来的东西，所以刻意保留，没有绕开。

## 预期与操作提示

AME 在 BF16 下的峰值是 8×8×16 = 1024 MAC/周期，40 MHz 下 41.0 GMAC/s。
RVV 侧的实际吞吐正是这个测试要测的，**这里不预设倍数** —— 上板的数就是答案。

两点操作上的提醒：

* **会明显慢**。矩阵乘占了每 token 的绝大部分，换成 RVV 后 ms/token 会成倍
  上升。跑满 256 个 token 的一问一答可能要等很久，
  演示时问一个能短答的问题即可，不必等它说完。
* **别拿它跟 L6 比"谁快"**，那个结论是预先知道的。有意义的数是**倍数**：
  同一个问题、同样的 pos，两版的 ms/token 之比。

## 怎么记录对比数

同一个问题分别在 L6_demo_opt 和本目录各跑一次，记下串口打印的 ms/token。
两版的提示符、时间戳、输出文字应当完全一致 —— 如果文字不同，说明有一边
拿错了权重或固件，数据作废。
